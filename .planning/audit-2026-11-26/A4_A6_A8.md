### A4-1 [bug] Chat messages are rendered as HTML, so anyone can inject markup
- Where: app/src/main/java/llm/slop/spazradio/ui/components/ChatContent.kt:331-342
- Evidence: each message goes through `HtmlCompat.fromHtml(msg.message, FROM_HTML_MODE_LEGACY)` into a TextView with
  `autoLinkMask = Linkify.WEB_URLS`. The broker has no login, so any client can publish `<font color="#000">`,
  `<big><big><h1>`, `<small>`, `<sup>`, `<img src=x>` (shows a placeholder glyph), `<blockquote>`, lists etc. and they
  render. Hidden `<a href>` targets are dropped (Linkify's `addLinks` removes existing URLSpans when the mask is
  set), but every visible URL-looking text, including bare `example.com`, becomes a tappable link. The web TV
  (liquid-lsd web/chat.js `cleanText` :35-46) strips tags, decodes entities and inserts only as `textContent`,
  linking only `http(s)://` and `www.` (:48-67). The checklist requires plain text with no markup or link injection.
- Impact: every chat viewer, whenever someone posts markup: giant/invisible/recoloured text, fake "system" lines,
  phishing links on any domain-like word.
- Fix: decode to plain text once in `ChatMessages.parse` (port `cleanText`: drop `<...>` tags, decode entities;
  cut to the caps *after* decoding as the TV does with `MAX_RECEIVED_TEXT`), unit-test it, and show the result in a
  plain Compose `Text` (or keep the TextView but `setText(plain)` with no `fromHtml`). Decide whether to keep
  linking; if yes, use `Linkify.addLinks` with a pattern limited to `https?://` / `www.` like the TV.
- Verified:

### A4-2 [bug] `onCleared` never disconnects: the launch runs on an already-cancelled scope
- Where: app/src/main/java/llm/slop/spazradio/ChatViewModel.kt:147-153
- Evidence: `onCleared()` does `viewModelScope.launch(Dispatchers.IO) { repository.disconnect() }`. In lifecycle
  2.8.6 (gradle/libs.versions.toml:8) `ViewModel.clear()` closes its closeables, `viewModelScope` included, before
  calling `onCleared()`, so this coroutine is cancelled before its body runs. The MQTT client (with
  `isAutomaticReconnect = true`, ChatRepository.kt:135) and `repositoryScope` (never cancelled) live on while the
  process does, and the retained presence `presence/<clientId>` keeps the nickname.
- Impact: the activity is destroyed while the radio service keeps the process alive (Back on API < 31, swipe from
  recents while playing). The old connection keeps reconnecting and receiving; reopening the app creates a second
  ViewModel/client (new clientId) so the phone holds two connections, and the user stays listed as online.
- Fix: call `repository.disconnect()` directly in `onCleared` (it is non-blocking; it launches on the repository's
  own scope). Also `close()` the paho client after disconnect and cancel `repositoryScope` at the end.
- Verified:

### A4-3 [bug] Disconnect while the connection is down leaves the old client auto-reconnecting (uncertain at runtime)
- Where: app/src/main/java/llm/slop/spazradio/data/ChatRepository.kt:211-231 (with :21, :66-67, :135)
- Evidence: `disconnect()` calls `mqttClient?.disconnect()` only `if (mqttClient?.isConnected == true)`, then sets
  `mqttClient = null`. If the link is down (paho is in its automatic-reconnect cycle) the old client is never
  disconnected or closed and keeps retrying. A later `connect()` (user joins again, ChatViewModel.kt:123-129)
  builds a new `MqttClient` with the **same** `clientId` (a `val` of the repository). MQTT brokers drop the older
  session when a second client connects with the same id, and both clients then auto-reconnect in turn.
- Impact: Reset nickname while offline, then rejoin: possible endless connect/kick ping-pong (battery, data,
  flickering "Connection lost" errors). Confirmed by reading only; needs an emulator run (airplane mode, reset name,
  online, join) to confirm the takeover loop.
- Fix: always `disconnectForcibly()` / `close()` the old client in `disconnect()` regardless of `isConnected`
  (wrap in try/catch), and only then drop the reference.
- Verified:

### A4-4 [bug] Leaving chat races the presence clear against the disconnect, so the nickname can stay "online"
- Where: app/src/main/java/llm/slop/spazradio/data/ChatRepository.kt:169-187 and :211-222
- Evidence: `disconnect()` calls `publishPresence(it, false)`, which only *launches* another coroutine to publish the
  retained empty presence, then immediately calls `mqttClient?.disconnect()` and nulls the field. The publish can
  run after the disconnect has started and fail ("Client is currently disconnecting" / not connected, caught and
  logged). A graceful DISCONNECT does not fire the last will, so the retained `presence/<clientId>` keeps the name.
  The web TV publishes the clear before `close()` in the same call (liquid-lsd web/chat.js `leave`, :240-246).
- Impact: after "reset nickname" the old name can remain in everyone's online list until someone overwrites that
  retained topic (effectively forever for that clientId).
- Fix: in `disconnect()` publish the empty retained presence synchronously (`client.publish(...)` on the IO
  coroutine, not via `publishPresence`) before `disconnect()`.
- Verified:

### A4-5 [bug] A reconnect while the app is in the background marks the user online again
- Where: app/src/main/java/llm/slop/spazradio/data/ChatRepository.kt:70-79; ChatViewModel.kt:114-121
- Evidence: `onStop` publishes an empty presence (offline), but `connectComplete` publishes
  `publishPresence(currentUsername, true)` on every (re)connect, with no notion of foreground. Paho's automatic
  reconnect (after any network change while the radio plays in the background) therefore re-announces the name.
- Impact: listeners who background the app show as online in chat for hours.
- Fix: keep a `foreground` flag in the repository (set from `onStart`/`onStop`) and announce only when it is true.
- Verified:

### A4-6 [bug] The presence roster has no bound: anyone can flood it with retained topics
- Where: app/src/main/java/llm/slop/spazradio/data/ChatRepository.kt:93-103, :207-209; ChatContent.kt:195-211
- Evidence: every `presence/<anything>` message adds an entry (copying the whole map each time), retained messages
  persist on the broker, and the expanded list is a non-lazy `FlowRow` of `SuggestionChip`s. A single script can
  publish thousands of retained names; every client receives all of them on subscribe. Names are capped, the count
  is not.
- Impact: slow startup/jank or OOM-ish memory use on every phone that joins chat, and an unreadable roster; lasts
  until someone clears the retained topics on the broker.
- Fix: cap the map (e.g. 200 ids; ignore new ids past the cap) and the shown chips (show "+N more"); consider
  ignoring topics with more than one level (`presence/a/b`). The web TV has the same unbounded roster
  (web/chat.js :174-180), so mirror the cap there.
- Verified:

### A4-7 [wrong] A failed or offline send throws away the draft
- Where: app/src/main/java/llm/slop/spazradio/ui/components/ChatContent.kt:264-270; ChatRepository.kt:194-206
- Evidence: the send button calls `onSendMessage(messageText)` and clears `messageText` at once. `sendMessage`
  returns silently when `mqttClient == null`, sets the generic error "Not connected" when disconnected, and reports
  publish exceptions only via `connectionError` (shown as raw "Connection Error: Send failed: ..."). The text is
  gone in every case. Checklist: "A failed send gives visible feedback and does not lose the user's draft."
- Impact: anyone typing during a dropout (tunnels, Wi-Fi handover) loses the message.
- Fix: make `sendMessage` return a result (or a suspend Boolean); clear the field only on success, otherwise keep
  it and show a short localized "Not sent" line. Disable Send while not connected.
- Verified:

### A4-8 [wrong] Nickname and outgoing text are neither trimmed nor capped (the TV caps both)
- Where: ChatContent.kt:89-102 and :245-247; ChatViewModel.kt:123-129, :139-145; ChatRepository.kt:203
- Evidence: the nickname field has no length limit and is stored as typed (leading/trailing spaces included; only
  `isNotBlank` is checked). Receivers (this app and the TV) cut names to 32, so a 40-character name is shown cut
  everywhere, including in the user's own echoed lines, while the roster shows the cut version too. Outgoing text
  is unlimited (receivers cut at 1000) and has no rate limit. The web TV trims, collapses whitespace and cuts the
  nick to 32 (web/chat.js :220), trims and cuts sent text to 500 (:231) and enforces `SEND_GAP_MS` (:234). No UI
  text states any limit.
- Impact: confusing truncation; the app is the easiest flooding tool for the shared chat.
- Fix: trim + collapse whitespace + `take(MAX_NAME)` in `setUsername`; `trim().take(500)` in `sendMessage`;
  `maxLength`-style filtering in both TextFields (and a counter, or hint text "up to 32 characters"); a minimal send
  gap like the TV.
- Verified:

### A4-9 [decision] The chat connection is open whenever the app is, chat panel open or not, foreground or not
- Where: ChatViewModel.kt:81-90, :105-121; MainActivity.kt:131
- Evidence: `ChatViewModel` is created with the activity (`viewModel()` default parameter), fetches history at app
  start and, if a nickname is saved, connects MQTT on every online event and stays connected (keepalive 60 s)
  while the radio plays in the background. Presence is announced on every `onStart` even if chat is never opened.
  The checklist item "Polling stops when chat is closed or the app is in the background" fails as written.
- Impact: a small but constant background connection and wake-ups for every user who ever joined chat; users are
  listed online while merely listening.
- Fix (owner's call): either accept and reword the checklist item, or connect only while the Chat page is shown
  (and for N minutes after), disconnecting in `onStop`.

### A4-11 [polish] MQTT client ids collide too easily
- Where: app/src/main/java/llm/slop/spazradio/data/ChatRepository.kt:21
- Evidence: `"mut" + Random.nextInt(1, 1000000)`: one million ids, shared with the web TV's namespace (it uses 6
