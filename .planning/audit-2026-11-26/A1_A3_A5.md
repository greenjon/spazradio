minSdk 24, targetSdk 36). It is a read-only review: no build and no device run. Items that need a device are listed
as owner checks.

## Findings

### A1-1 [bug] Unplugging headphones does not pause playback
- Where: app/src/main/java/llm/slop/spazradio/RadioService.kt:147-151
- Evidence: the `ExoPlayer.Builder` never calls `setHandleAudioBecomingNoisy(true)`, and `ACTION_AUDIO_BECOMING_NOISY`
  is handled nowhere else (grep `BecomingNoisy` finds nothing). ExoPlayer's default is false. The A1 checklist
  expects unplugging to pause.
- Impact: a listener who pulls out wired headphones or turns off a Bluetooth headset has the radio carry on from the
  phone speaker, every time, on every device.
- Fix: add `.setHandleAudioBecomingNoisy(true)` to the builder.

### A1-2 [bug] Reopening the app stops an archive that is playing in the background
- Where: app/src/main/java/llm/slop/spazradio/RadioViewModel.kt:152-170
- Evidence: when a new `RadioViewModel` connects its controller, `_appMode` is always the default RADIO. With
  autoplay on, it calls `showLiveStream()`, which replaces any non-live item with the live stream. With autoplay off,
  it calls `controller.setMediaItem(LiveStream.mediaItem(...))` and sets `playWhenReady = false`. In both cases an
  archive the service is playing is replaced. A new VM is created whenever the Activity is finished and launched
  again (back out to home while an archive plays, then tap the launcher icon or the notification). The service
  survives in the same process.
- Impact: someone listening to an archive show who backs out of the app and taps the notification to see the
  position loses the show. With autoplay on, the live radio starts in its place.
- Fix: in the controller-connected callback, if `controller.currentMediaItem` is a non-live item, start in
  `AppMode.ARCHIVES` (or at least leave the item alone), and only apply the RADIO/autoplay logic when the current item
  is live or there is none.
- Verified:

### A1-3 [bug] "Reconnecting…" is shown but nothing ever reconnects
- Where: app/src/main/java/llm/slop/spazradio/RadioViewModel.kt:206-209, 261; RadioService.kt:180-189
- Evidence: on `onPlayerError` the VM sets `PlaybackUiState.Reconnecting`, and `STATE_ENDED` also maps to
  Reconnecting. But no code re-prepares the player after an error or after the end of a live stream. The service's
  only error handling is the low-mount 404 fallback. A terminal ExoPlayer error leaves the player IDLE. The stream
  comes back only when the user presses play (`togglePlayPause` → `showLiveStream` → `prepare()`). This is also the
  path for an Icecast source drop (stream ENDED) and for a network loss that outlasts ExoPlayer's own load retries.
- Impact: after a short network drop, or when the station's source restarts, the radio goes silent while the header
  says "Reconnecting…" forever. This is likely in a car or on a train.
- Fix: in `RadioService`, on a network-class `PlaybackException` or on `STATE_ENDED` for the live item while
  `playWhenReady`, schedule `prepare()` with capped backoff (for example 2, 4, 8, 16 s, then every 30 s). Also retry
  at once from the `ConnectivityManager` callback when a network comes back. Cancel the retry on user pause or stop.
  Show the plain error once the retries stop.
- Verified:

### A1-4 [bug] Notification and lock-screen title stay blank until the song changes
- Where: app/src/main/java/llm/slop/spazradio/RadioService.kt:284-301
- Evidence: `fetchAndUpdateMetadata` returns early when `metadata == lastMetadata` (`:284`). It only writes the
  title into the media item when the live item is audible (`:292-294`). `lastMetadata` is set either way. So if the
  first poll runs while the player is paused or stopped (autoplay off, Archives tab, before the user presses play),
  that title is never applied. A fresh live item made by `LiveStream.mediaItem()` (switching back from Archives,
  `RadioViewModel.kt:351, 389`) also has no metadata. In both cases nothing is applied until `/playing` returns a
  different title, which can be an hour or more for a long show.
- Impact: the notification, lock screen, Bluetooth display and car head unit show no title (or the app name) for
  most sessions that do not autoplay.
- Fix: keep the last metadata and apply it whenever the live item becomes audible. Either drop the
  `lastMetadata` early return for the media-item update, or call the apply step from an `onIsPlayingChanged` /
  `onMediaItemTransition` listener in the service. Alternatively, set the metadata in `LiveStream.mediaItem` from
  `metaDataFlow.value`.
- Verified:

### A1-5 [bug] (uncertain) No wake mode for network streaming; WAKE_LOCK is declared but unused
- Where: app/src/main/java/llm/slop/spazradio/RadioService.kt:147-151; AndroidManifest.xml:10
- Evidence: there is no `setWakeMode(C.WAKE_MODE_NETWORK)` on the player, and nothing uses the `WAKE_LOCK`
  permission. ExoPlayer's docs recommend `WAKE_MODE_NETWORK` for streaming with the screen off, so that CPU and Wi-Fi
  locks keep the loader fed. The foreground service keeps the process alive but does not hold the Wi-Fi lock.
- Impact (unconfirmed): with the screen off on Wi-Fi, some devices put the Wi-Fi radio into power save and the
  stream stutters or stalls. A long screen-off session on a real phone would confirm it.
- Fix: add `.setWakeMode(C.WAKE_MODE_NETWORK)` to the builder (it uses the existing WAKE_LOCK permission). Also
  update PRIVACY.md's permission text if it does not already explain WAKE_LOCK.

### A1-6 [polish] /playing is polled every 10 s for the service's whole life; no pause timeout
- Where: app/src/main/java/llm/slop/spazradio/RadioService.kt:264-272, 310-314
- Evidence: `startMetadataPolling` loops from `onCreate` to `onDestroy`, whatever the playback state. The service
  stays started after a pause in the background (media3 1.4 has no idle-service timeout, and the code adds none), so
  a paused app in the background polls `radio.spaz.org/playing` 8,640 times a day until the user swipes it away or
  the system kills it. The paused notification stays up the whole time.
- Impact: small but needless mobile data and battery use, and a lingering paused notification. The A1 checklist
  expects a pause timeout.
- Fix: poll only while playing or while a controller (the UI) is connected. Stop the service (`stopSelf()`) after
  about 10 minutes paused in the background, or upgrade media3 to a version with a built-in timeout. Decide which.
- Verified:

### A3-1 [bug] Downloads silently fail on Android 7-9
- Where: app/src/main/java/llm/slop/spazradio/utils/DownloadTracker.kt:43-57; app/src/main/AndroidManifest.xml:5-10;
  app/build.gradle.kts:80
- Evidence: minSdk is 24. Before API 29, a `DownloadManager` request with `setDestinationInExternalPublicDir`
  needs the caller to hold `WRITE_EXTERNAL_STORAGE`, and `enqueue` throws `SecurityException` otherwise. The manifest
  has no storage permission (git `-S` finds that it never had one), and the exception is only logged (`:55-56`).
  `getDownloadedUrls`/`refreshDownloadedFiles` listing `Music/SPAZRadio` would also need READ before API 29.
- Impact: on Android 7, 8 and 9 phones, tapping download in the list or the header does nothing at all. No spinner,
  no message.
- Fix: add `<uses-permission android:name="android.permission.WRITE_EXTERNAL_STORAGE" android:maxSdkVersion="28"/>`
  and request it at download time on API < 29, or download into `getExternalFilesDir(DIRECTORY_MUSIC)` on old
  versions. Surface the enqueue failure (A3-5). PRIVACY.md would then need the permission explained (lane A8).
  Confirm on an API 28 emulator image first.
- Verified:

### A3-2 [bug] One malformed feed item cuts the archive list short
- Where: app/src/main/java/llm/slop/spazradio/data/ArchiveRepository.kt:62-64, 75, 117-121; ArchiveViewModel.kt:114-118
- Evidence: the parse runs inside one try. `parser.nextText()` on a `<title>` that contains a child tag (raw HTML
  such as `<b>`) throws, and so does an undefined entity such as `&nbsp;` (KXml is not relaxed). The catch then falls
  through to `shows`, which holds only the items before the bad one. It is not cached (the save sits inside the try),
  but `fetchArchives` uses any non-empty result as `allShows`, replacing the full cached list in memory, and the hourly
  poll keeps doing so.
- Impact: if the station adds one show whose title has an `&nbsp;` or a tag, every show after it in the feed
  disappears from Archives and from search. It also makes those shows unfindable for the header download.
- Fix: parse each item defensively. Catch per item and skip it, or read titles with `parser.text` while tolerating
  nested tags. Alternatively, treat a parse exception as a failed fetch (return empty, keep the cache). The minimal
  fix is `return@withContext emptyList()` in the catch, so the old list stays.
- Verified:

### A3-3 [bug] (uncertain) After a reinstall, downloaded shows look not-downloaded and get downloaded twice
- Where: app/src/main/java/llm/slop/spazradio/utils/DownloadTracker.kt:41, 99-107; ArchiveViewModel.kt:347-362, 417-424
- Evidence: "downloaded" means "file name appears in `File(Music/SPAZRadio).list()`". Under scoped storage
  (API 29+), the File API lists other apps' audio files only with READ_MEDIA_AUDIO/READ_EXTERNAL_STORAGE, which the
  app does not hold. After uninstall and reinstall (or a new phone with restored data), the old files are no longer
  attributed to the app. If they are hidden, the shows show as not downloaded, `getLocalFileIfDownloaded` misses them
  (so they stream instead of playing locally), and downloading again makes DownloadManager write a de-duplicated name
  (`name-1.ogg`) that the app never matches. The app then shows not-downloaded forever and allows endless copies.
- Impact (unconfirmed): duplicate multi-hundred-MB files in Music after a reinstall.
- Fix: confirm on an API 33+ emulator. Download a show, uninstall without clearing Music, reinstall, and open
  Archives. If confirmed, query MediaStore by `RELATIVE_PATH`+`DISPLAY_NAME`, or keep downloads in app-specific
  storage. Decide which, since the files are meant to be visible to music players.
- Verified:

### A3-4 [bug] Download set updated with a non-atomic read-modify-write from two threads
- Where: app/src/main/java/llm/slop/spazradio/utils/DownloadTracker.kt:52, 90, 96
- Evidence: `_downloadingUrls.value += show.url` runs on the main thread (`startDownload`). `-= url` runs on
  `Dispatchers.IO` (the polling coroutine). `value += x` is get-then-set, so one update can overwrite another. A URL
  can then stay "downloading" forever, or a new download can lose its spinner. `activeDownloadIds` (a plain
  `mutableMapOf`) is written from both threads too, but it is never read.
- Impact: rare. Two downloads finishing together, or a tap at the moment another finishes, leaves a stuck spinner
  that also blocks downloading that show again until restart (`:41`).
- Fix: `_downloadingUrls.update { it + show.url }` / `update { it - url }`. Delete the unused `activeDownloadIds`.
- Verified:

### A5-1 [bug] Built-in EQ keeps the old sample rate's filters after a format change
- Where: app/src/main/java/llm/slop/spazradio/Equalizer.kt:165-170, 195-202
- Evidence: coefficients are recomputed only when `target != applied` or the channel count changes. When the sink
  reconfigures the processor for a new format, `BaseAudioProcessor.flush()` makes the new `inputAudioFormat` current
  and calls `onFlush()`, which only zeroes the state. `applied` keeps its value, so `coeffs` stay computed for the
  previous `sampleRate`. `onReset()` (which clears `applied`) runs only on a full sink reset.
- Impact: when a listener with the Built-in EQ on moves between sources at different rates (live 44.1 kHz vs. an
  archive at 48 kHz, or a low mount at 22.05 kHz if it differs), every band sits at the wrong frequency (off by 9% up
  to 2x) until they move a slider. EqualizerTest does not cover a rate change.
- Fix: in `onFlush()` set `applied = null` (keep the state reset). Or store the sample rate with `applied`, and
  recompute when it differs. Add a test that configures 44100, then 22050, and checks the response.
- Verified:
