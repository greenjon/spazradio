### A2-2 [bug] One malformed schedule entry blanks the whole schedule
- Where: ScheduleViewModel.kt:131-147, :162-183 (also :72-83 for the cache)
- Evidence: `RawShow.name: String` is non-null, but Gson builds the object reflectively, so a missing or `null` `name` is stored as null. `Html.fromHtml(show.name, ...)` (:176) then throws NPE inside `validShows.map { formatShowItem(it) }`. The exception is caught by the loop at :149, retried once, and ends as `_error = "Schedule unavailable"` (only when the list is empty), with nothing saved to the cache. A non-array body (`{}` or `null`) fails the same way. The web TV filters bad rows individually (schedule.js:34-35, `Number.isFinite`, `end > start`, fallback name "SPAZ RADIO"); the app does not. Missing timestamps become 0 (silently dropped by the `end > now` filter, fine), but there is no `end > start` check.
- Impact: a single bad row from the server hides the whole schedule for every user until the server fixes it. A cached copy is used only if it predates the bad row.
- Fix: make `name` nullable (`String?`), `mapNotNull` with a try/catch per item, fall back to "SPAZ Radio" like the web TV, and skip `end <= start`. Add a unit test for null name and a non-array body (formatShowItem is private; move the parse into a small testable object like NowPlaying).
- Verified:

### A2-3 [polish] Polling is not tied to app visibility
- Where: RadioService.kt:264-272 (started in onCreate :200, only cancelled by `serviceJob.cancel()` in onDestroy :318); ScheduleViewModel.kt:90-98
- Evidence: the /playing poll runs every 10 s for the whole life of the service, including while paused with the screen off, as long as the service is alive (MediaSessionService can stay up while a controller is connected). The schedule poll runs hourly from ViewModel creation (RadioApp at launch), even if the user never opens the schedule, and keeps running while the process is in the background. The audit item says polling should stop when backgrounded.
- Impact: small battery/data cost (10 s poll is one tiny JSON); only matters when the service lingers while paused. Playing in the background legitimately needs the poll (notification title).
- Fix: in RadioService poll only while `isPlaying`/session active (or lengthen to 60 s when paused); schedule poll can be demand-driven (`repeatOnLifecycle(STARTED)` or fetch when the panel opens). Otherwise record as accepted.
- Verified:

### A2-4 [polish] Schedule rows are formatted once, so they go stale
- Where: ScheduleViewModel.kt:75-82, :144-146
- Evidence: `ScheduleItem` holds pre-formatted strings, built at fetch/cache-load time with the then-current locale and time zone, and the list is filtered by `end > now` only then. The poll interval is 1 h. After a time zone change, an in-app locale change, or when a show ends, the list is wrong until the next poll (up to an hour; a show that ended 50 minutes ago still appears first). Also an empty valid list (fetch OK, no upcoming shows) shows a blank panel with no message (InfoBoxContent.kt:395-399). Also a cache-read race: loadFromCache (:68) is launched without ordering against the first network load, so a slow cache read could overwrite fresher network data with the stale list.
- Impact: cosmetic; wrong row at the top for up to an hour.
- Fix: keep `RawShow` in state and format/filter in the composable (or re-filter on `ON_RESUME`); show a "No upcoming shows" string when empty; guard the cache load with `if (_schedule.value.isEmpty())`.
- Verified:

### A2-5 [wrong] Schedule error state shows "Connecting…" and the real message is never displayed

### A7-3 [bug] AUTO theme under system dark draws light system-bar icons wrongly
- Where: MainActivity.kt:90-110
- Evidence: `isDarkTheme = appTheme == DARK || appTheme == NEON`. For `AppTheme.AUTO` it is false even when the system is dark, while SpazRadioTheme (Theme.kt:57-66) picks the dark color scheme. The branch then calls `SystemBarStyle.light(...)`, which draws dark status/nav icons on a dark background. The check also runs only when `appTheme` changes, so a system dark-mode flip while AUTO is selected is only picked up if the activity is recreated (uiMode is not in `configChanges`, so it is recreated; fine). Also, in the Neon theme with gradient bars okay.
- Impact: with AUTO selected and the phone in dark mode, the clock, battery and nav icons are near invisible on the dark background (and the reverse mismatch cannot happen).
- Fix: `val isDark = when (appTheme) { DARK, NEON -> true; LIGHT -> false; AUTO -> isSystemInDarkTheme() }`, compute inside the composable, and key the LaunchedEffect on it. Owner check on device.

### A7-4 [bug] Neon: "Reset Chat Username" button text is unreadable
- Where: InfoBoxContent.kt:275-281; Theme.kt:41-52
- Evidence: the button uses `containerColor = colorScheme.error` with fixed `contentColor = Color.White`. NeonColorScheme (`darkColorScheme(...)` without `error`) leaves `error` at the Material default 0xFFF2B8B5 (light pink). White on F2B8B5 is 1.7:1. LunarizedDark/Light set `error = LunarizedRed`, where white is 5.3:1, so only Neon is affected. The same pink is used for ErrorContent text (InfoBox.kt:94) on the Neon dark overlay, which is readable, but the button is not.
- Impact: Neon is the default theme; the destructive button label is nearly invisible.
- Fix: use `contentColor = MaterialTheme.colorScheme.onError` (and set `error`/`onError` explicitly in NeonColorScheme, e.g. a hot red/white), instead of `Color.White`.
